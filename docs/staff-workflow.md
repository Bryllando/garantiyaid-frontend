# Staff workflow — Barangay, DSWD and Admin

This guide describes the current application. The sponsoring office must approve its program requirements and staff authority before a real government pilot. Wallet credits and biometric fixture tests are simulated; recording a notification is not evidence of SMS delivery.

For the proposed Cebu City scope, use the [government procedure and current role matrix](../../garantiyaid-backend/docs/government-procedure.md) and [office review record](../../garantiyaid-backend/docs/government-procedure-review.md). No partner office or named service has approved this procedure yet.

## Normal journey

1. **Barangay: register the beneficiary.** Search first to avoid a second record. Check the assigned barangay, name, birth date and address. Review the form before registering. Registration alone does not enroll the person in a program.
2. **Barangay: upload the supporting documents.** Open the exact beneficiary and choose the active program above the document list. Its named requirements appear directly in the Document type dropdown (for example, Request letter). Choose each name and upload its readable file, or use Upload beside a missing requirement to select it automatically. Each name needs a separate file and review. A successful upload appears in the document list as submitted. One file does not satisfy several different named requirements.
3. **Barangay: submit enrollment.** Select the program and choose **Submit enrollment**, then **View submitted enrollment**. Give the independent reviewer this enrollment link. Admin and DSWD can also submit, but cannot review their own submission.
4. **DSWD / independent Admin: review enrollment.** Open **Enrollment review**, select the case and use **Preview** beside each document's Download button to inspect the uploaded PDF or image. Previewing leaves its review status unchanged. Select **Start validation**, then explicitly Accept or Reject each submitted document. Check every required document and eligibility result, then approve, request correction with a specific reason, or reject with a recorded reason. Approval is separate from event assignment.
5. **Admin: prepare the distribution.** Use the approved enrollment's program link or the beneficiary's **Assistance progress**. Select the correct draft event, prepare sessions and capacity, allocate approved beneficiaries, and generate the queue. For physical assistance, define the package/item, unit and whole-unit quantity per beneficiary; use **Open event > Edit assistance package** to adjust a draft even after sessions are prepared. Review the package, names, service areas and appointments before **Open distribution event**. Opening locks package, session, allocation and scheduling changes. Issue QR credentials where required and use the office's approved notification process.
6. **Verification staff: complete only the event-required identity checks.** Use the exact event and beneficiary from the queue or assistance progress. QR can be checked by Admin, DSWD or assigned Barangay staff. Live face and signature verification are handled by DSWD / assigned Barangay staff. Review the credential before confirming. A combined check remains pending until every required part passes. Follow the claim's **Continue identity checks** action when a part is missing.
7. **Record the actual completion.** For physical assistance, assigned Barangay staff open the exact claim, check the full package is available, complete the handover and obtain acknowledgment. Enter the actual **Quantity handed over**, evidence type and traceable log reference (for example, log identifier, page and row), then **Mark released**. A quantity different from the event package cannot complete the claim; escalate a shortage or substitution. Older events opened without a package retain the reference-only workflow and unknown quantities. For the simulated wallet, DSWD reviews the verified claim and records **Credit verified claim**. Verification alone is not a handover, credit or receipt.
8. **Issue the receipt.** Open **Claims and receipts** for that claim and choose **Issue receipt** after completion. Review the event, recipient, package/quantity and evidence before printing. Retain the signed acknowledgment using the office's records procedure. Reopening an issued receipt preserves the original snapshot; a later dispute remains part of the claim history. A system receipt does not establish government approval or replace the office's required form.
9. **Admin: reconcile and close.** Open the event's **Distribution reconciliation**. Follow every finding to its affected record, resolve active disputes, finish pending verification / release, and issue missing receipts. Compare package units in the report and signed release log, including quantities on voided claims and older handovers without quantities. Voiding a claim does not record a return of goods. Check attendance and prepare the report. Refresh the review, then **Close distribution event**, enter a closure note with the signed-log/closing-sheet reference and confirm. The server checks again. Closure marks only unvisited appointments whose time slots have ended as missed, closes slots and revokes unused active QR credentials. Releases, allocations, receipts and checked-in attendance are preserved. Closure cannot be undone in this workflow.

In **Supporting documents**, use **Preview** beside Download to inspect an uploaded PDF, JPG or PNG. **Remove** requires confirmation and is available for submitted or rejected uploads. Removing stops the file from satisfying program requirements; the stored file and audit history are retained. Accepted/superseded files are protected, and a file attached to a burial referral must first be detached from that editable referral.

## Archiving a barangay

Admin opens **Staff and barangays → Barangays → Archive** on the service area no longer in use. Reassign or deactivate its active Barangay Facilitators first, and close or cancel its draft/open distributions using the existing event procedure. The server blocks archiving while either remains.

Confirm **Archive barangay** to move it to **Archived barangays**. This reuses the existing inactive status: previously inactive barangays also appear in that list. New staff assignments, beneficiary registrations and distribution events require an active barangay. Linked records, receipts and audit history are retained; no barangay is permanently deleted.

Use **Archived barangays → Restore barangay** when the area is needed again. Restoration returns it to active service areas and does not reactivate staff accounts. Archive and restore record the administrator and status change in the audit log. If the response is interrupted, retry the same confirmation or refresh and inspect the current/archive list before continuing.

## Exceptions and recovery

For burial requests handled by an external office, follow the [burial referral and printable-letter workflow](../../garantiyaid-backend/docs/burial-referrals.md). Start from the living applicant's beneficiary record. Barangay prepares, DSWD reviews, the designated officer signs offline, and staff records issuance and the actual office response. This is separate from enrollment and distribution claims; it does not approve assistance or guarantee payment.

| Situation | Next action and responsible staff |
| --- | --- |
| Missing or rejected required document | Barangay / Admin opens **Correct beneficiary documents**, uploads the missing file or replaces the rejected file, then **Return to enrollment review**. Resubmission stays disabled until required types have a submitted or accepted document. Review the correction note and resubmit. A different authorized reviewer starts validation; DSWD accepts the replacement before approval. |
| Enrollment rejected, suspended or withdrawn | Read the decision and provide the exact enrollment reference to the authorized program reviewer. Do not create another person or treat the enrollment as approved. The app does not automatically reopen a final decision. |
| No event or allocation | Admin prepares an appropriate event and assigns the approved enrollment while it is a draft. An event listed in assistance progress does not mean the person is allocated. |
| No appointment or cancelled appointment | In a draft, Admin / assigned Barangay staff generate the queue or reactivate an allowed cancelled appointment. Once opened, ask Admin to review the exact event and beneficiary before arranging another eligible visit. There is no walk-in bypass. |
| Missed visit | Barangay checks attendance with Admin using the exact beneficiary and event reference. Preserve the original missed visit. Admin reviews eligibility and prior assistance before arranging any later event. A future appointment cannot be marked missed early by closure. |
| Used QR or duplicate claim | Choose **Review existing claim** from the QR error. Check remaining verification, prior release and any hold. Repeated scanning is not a recovery action. If flagged, file the beneficiary concern for independent review. |
| Incomplete face / QR / signature | Open the existing claim and follow the remaining-check action. Complete the missing part for the same person and event. Do not issue a receipt or record release while pending. |
| Face mismatch / failed liveness | Confirm the correct person and profile, check lighting and consent, then authorized verification staff make a new live attempt for the same event. Admin can review identity records and coordinate with the capture staff. A mismatch is not proof of fraud. |
| Face service unavailable | Keep the claim pending and retry after service recovery. **Retry claim verification** returns to verification, not replacement of the enrolled face profile. |
| Held face profile / invalid consent | Open the duplicate review or profile-and-consent record indicated by the attempt. Only the authorized review or consent process can clear the issue. If the required check cannot be completed, escalate to the process owner; this app has no manual release override. |
| Representative arrives / inaccessible verification | Refer to the process owner using the exact record. This flow does not record representative authority or bypass required identity checks. Agree on an accessible procedure before using this service for affected beneficiaries. |
| Shortage, partial handover or substitution | Preserve the actual evidence and refer to the accountable officer. Do not enter the planned quantity when it was not received. The current flow completes only the full configured package. |
| Active claim dispute | Open the linked case. A different authorized Admin / DSWD reviewer starts the review; only its assigned reviewer records the decision. The filer cannot self-review. A changed case or claim requires a refresh before deciding. Clearing a hold does not itself verify or release assistance. |
| Failed record load | Use the screen's refresh / retry. Do not interpret failed loading as zero claims or missing requirements. Decision and closure controls remain unavailable until the required evidence loads. |
| Slow save / uncertain release response | Wait while saving. For an uncertain release, retry the existing confirmation so the original request and evidence are reused. If you have left the screen, inspect the exact claim before entering another release. |
| Outage before saving a handover | Preserve office evidence and use its approved continuity process. The app does not backdate or import offline handovers. Inspect the existing claim before retrying or handing out goods again. |
| Session expired | Sign in again, reopen the exact record and check its latest state before continuing. Unsaved form content is not guaranteed to survive sign-out. |
| Closure conflict | Keep the closure note, review the refreshed findings and resolve them before retrying. A lost successful response can be retried without rewriting the original closure note or audit record. |
| Closed / cancelled event | Review preserved claims, receipts, reports and concerns. Further verification and release are unavailable. Refer an unresolved visit to Admin using the original event and beneficiary references. |

Biometric **review drafts** are saved only in the signed-in tab. Other staff cannot see them; saving a draft does not submit a referral or resolve a shared case. Use the office's existing handoff process and the exact record link. Claim disputes and face duplicate reviews use their actual shared case screens.

## Acceptance checklist

Use the [supervised pilot session guide](../../garantiyaid-backend/docs/supervised-pilot.md) and [blank record](../../garantiyaid-backend/docs/pilot-session-template.md) for task observations, issues, retesting and handover. Recorded physical handovers and package units include handovers on voided claims; the value of completed claims excludes them. Compare exact claim/log/receipt references before closing.

During maintenance or recovery, follow the [staff outage rules](../../garantiyaid-backend/docs/pilot-recovery.md#staff-outage-rules). The operator must reconcile saved handovers and account changes before reopening. Record actual device/staff results in the [pilot review](../../garantiyaid-backend/docs/pilot-review.md).

Use separate Barangay, DSWD and Admin accounts and synthetic beneficiary data first. Follow steps 1–9 and the exception table without editing the database. Confirm that all roles see the same approval, verification, completion and receipt facts. Repeat the task forms on the staff devices with keyboard-only navigation. Record the failed step, role, event and record reference without copying credentials or biometric data.

Batch 2 automation uses fixture APIs and mocked database tests. Batch 3 adds [real API/database and browser acceptance](../../garantiyaid-backend/docs/integrated-acceptance.md), including competing staff requests and interrupted responses, using an isolated disposable PostgreSQL instance. Face scores, wallet credits and SMS remain simulated; simulated face results are labeled on receipts. Actual office approval, hardware testing and supervised staff acceptance remain later gates.
